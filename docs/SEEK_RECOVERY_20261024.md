# RM 定位取消恢复与有界缓存补充

日期：2026-10-24。本记录补充同日的 `COMPLETION_20261024.md`，不覆盖其中的既有发行包摘要。

## 已修复的问题

`Seek` 向前解码途中，IStream 取消可以发生在已跳过部分 PCM 后。此前失败时没有恢复调用前的逻辑位置，后续 `Read` 从扫描中间继续，丢失尚未交付的声音。Cook 样本复现为：调用前只读取 4,096 字节，本应还有 2,936,832 字节，却只返回 1,638,400 字节。

现在失败的 `Seek` 保持请求时间参数不变，并记录调用前位置；下一次 `Read` 从头准确重建解码状态至该位置。恢复期间再次取消仍保留同一个恢复目标。错误 HRESULT 不改成成功；失败时不会把扫描中间位置发布给宿主。

定位期间已经解出的 PCM 也进入原有 4 MiB 历史缓存，因此远距离前跳后在附近来回拖动不必再次读取源文件。缓存限制、输出精度和声道布局不变，没有增加额外运行 DLL 或系统 API。

## 为什么没有直接增加压缩包位置索引

固定 FFmpeg 9.0.2 的 `libavformat/rmdec.c::rm_read_seek` 提供容器索引跳转，但它只定位包并清空包计数。Cook 的 `libavcodec/cook.c` 还有前帧重叠、前后增益及状态。容器时间戳和字节偏移不能单独恢复与完整解码逐字节一致的 PCM。

这次保留缓存外的准确重放。以后若实现快速检查点，需要按编码保存并恢复解码器状态及交织状态，建立明确的状态版本和失效规则；不能把 FFmpeg 私有上下文指针直接复制为通用快照。该索引优化仍未完成。

## 本轮验证

本机 Windows 11 上对 Cook、ATRAC3、SIPR、AAC、RA28.8、DNET、MP3 ADU，以及两种 VQF 样本执行联合定位矩阵。VQF 同时覆盖原回调预热与直接 Read。45 次进程运行均成功，共完成 243 个定位/故障场景；44 个未触发 I/O 的故障注入分支明确标记为 SKIP，不计作已注入故障。

- 定位到 0、1 ms、中间、末尾附近、末尾和 DWORD 最大时间，输出与同一 DLL 完整解码的切片相同。
- 远距离定位后的 500 ms 回退，PCM 相同且源读取字节数不增加。
- 前向/后向定位中的读取消、已消耗 13 字节后取消、底层 Seek 取消、恢复期间再次取消，恢复 PCM 与调用前未交付部分相同。
- 已知截断的 RA14.4 样本仍在尾部返回 `0x8007000D`，有效前缀 1,741,440 字节；重新定位到 0 后前缀相同。没有把损坏样本伪装为正常 EOF。
- 额外重跑 Cook 的 8 组 Read 取消矩阵，通过。
- MSVC Win32 Release 构建及 XP/Win7 静态导入检查通过（5 个系统 DLL、154 个导入）。最终 `2026.10.24p1` DLL 已在 XP SP3、Win7 SP1 和 Windows 11 完成联合 45 项矩阵，各系统失败为 0。原版与重建版的 Cook RM 实际播放在三系统通过。
