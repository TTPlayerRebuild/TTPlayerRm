# SIPR 增益、高通及错误帧入口核查（2026-11-05）

本轮在 `2026.10.29p1` 的谱参数和激励插值修复上，恢复低码率增益、低码率末端高通以及 16 kbps 增益的原始浮点存储顺序。六个实际有效音频区间的 PCM 差异均减少，最大差仍为 1 LSB；没有修改 PCM16 量化，也不宣称整个解码内核逐位一致。

本轮另以原 DLL 的正常导出调用补齐有效帧位图、短输入及重置探针。原 RM 文件播放路径固定传入全有效位图，不能把 DLL 对其他调用方提供的丢包隐藏等同于本插件需要复刻的文件输入行为。旧 16k `RAFlush`／`RAInitDecoder` 留下的部分历史也没有成为新 Reader 的兼容目标。

## 数值实现及原因

原文件仍是用户提供的 `RealCodec/sipr.dll`，SHA-256 为 `0d78d1da2979b332234e0942c479842fe4333d0d5197c3bb6b54543c647bebbd`。本轮没有修改该 DLL；正常加载使用工作区既有的私有 MSVCR71，生产插件不增加旧 DLL 或旧运行库依赖。

1. 低码率增益 `614a9660`：按原顺序累计 48 项能量，分别把测量 dB、预测 dB 和最终增益存为 float，再把 PCM 单位的增益转换到 FFmpeg 的归一化单位。原四项能量历史保留在当前 `SiprContext`。独立对照的 256 个增益码本 float 与上游完全相同，原因是计算及存储顺序，未改动码本。
2. 低码率高通 `614aa020`：原函数分别保存前两个输入和前两个输出，五项乘加后存 float。上游的两状态等价滤波器具有不同的舍入历史。新实现使用原系数及累计顺序，四项状态均归属 Reader。
3. 16k 增益 `614ab940`：恢复 80 项能量、两项预测及最终增益的 float 存储点。32 个增益码本 float 没有差异。最终量化的原汇编 `614a3053..614a3060` 从已存储 float 加 double `0.5` 再向零取整，与既有 Reader 量化规则一致，不应再次修改量化。

低码率函数的既有 REA 证据分别为 `ev_fb28009a64a9f232ded60f13449a16ac4799efc172dafd383eed5dd2a2e55350`、`ev_4a3a767c10c4861fd52531dde764434060b65b30f3af4e2717c39b8ee5249395`。16k 增益与输出转换复用同一原文件的既有完整汇编 `plugins_followup_20261029/sipr/original-asm.txt`，关注 `614ab940..614abaa6`、`614a3053..614a308c`。伪代码不是原源码；关键 float 存储点均核对汇编，并以正常调用原函数验证。

生产改动位于 `cmake/sipr_legacylow.h`、`cmake/sipr_legacy16k.h`、`cmake/legacy_sipr.py`。补丁把私有 `SiprContext::highpass_filt_mem` 在 `TTP_RM_LEGACY_SIPR` 开启时扩为四个 float，关闭时仍为上游两个。整个 RM 后端统一启用此宏，必须完整重编译 `sipr.c`、`sipr16k.c` 等对象；不能把新布局对象与旧对象混用。现有 CMake 依赖和完整源码摘要已经包含这些补丁及头文件。

这里的宏关闭验证隔离 SIPR 数值补丁，使用原解复用基线；统一构建另启用严格短包检查。不能把解复用行为变化错误归因于 SIPR 数值宏，也不能拿旧的宽松解复用尾包作为新 Reader 的有效音频。

本轮重新分别比较增益、高通及两者组合。高通在当前激励插值基线上已能改善四个低码率样本；组合后全部低码率样本均优于 p1。因此前轮“高通／增益候选未改善”的结论描述的是当时试验组合，不应继续当作当前基线的结论。增益单独应用会使一个 5k 样本略差，生产没有按样本选择算法，而是统一恢复有独立函数证据的两条路径。16k 交叉淡化候选没有改善最终 PCM，未合入。

## 16k 历史尾部结论的纠正

既有 [FATE 16k 文件](https://fate-suite.ffmpeg.org/sipr/) 本来只有 100,000 字节。独立于 FFmpeg 的 RM 字段和包长度核算得到：交织参数 `h=6, w=320`，34 个完整组；最后音频包从偏移 99,925 开始，声明 332 字节（含 12 字节包头），实际只有 75 字节，即 320 字节音频数据只剩 63 字节，缺少 257 字节。该组前五行完整，第六行不完整。

34 个完整组对应 `34×6×320÷20=3264` 个 codec 包、522,240 个 PCM 样本。旧解复用没有检查 SIPR 分支的 `readfull` 返回值，仍输出最后一个缺损组，多出 96 个 codec 包即 15,360 样本。把这些包交给原 DLL 仍能解码，不证明这些音频来自真实完整输入。**前两轮“额外 15,360 样本是有效尾音／不应复制原宿主提前终止”的结论撤回。** 新版保留 522,240 有效样本并返回 `ERROR_INVALID_DATA`，与旧宿主在这个输入上的边界一致。

新的正常 16k 样本来自官方完整 [intro.rm](https://samples.ffmpeg.org/real/AC-sipr/intro.rm)，247,227 字节，SHA-256 `7d11b45d9933f5986f4535843cacad7c36607314d17c52ab3444e286d02aa4cc`。其 DATA 对象在偏移 245,485 结束，之后是完整索引；738 个完整音频包组成 123 个交织组，无剩余行，输出 1,889,280 样本并正常结束。没有修改头部、填零或拼接音频。旧 FATE 文件继续作为独立截断负例保留。

6.5/8.5k 两个旧文件分别拥有 35/12 个完整音频交织组，尾部截断在视频包；音频前缀仍为 483,840/165,888 样本。它们的有效 PCM 没有因严格短包检查改变。私有 `container-audit.json`、`intro-container-audit.json` 与 `full16-results.json` 保存独立计数和直接 API 结果。

## 错误帧位图与原宿主实际调用

既有反编译遗漏了 `RADecode` 的第六参数；原汇编 `614a1113` 读取 `[ebp+1Ch]`，`614a1130` 以 `ret 18h` 返回，确认正常导出是六参数调用。`614a1650` 向各模式传递这个有效帧位图地址；各模式每解一帧右移一位，0 位进入丢包隐藏，1 位按压缩数据解码。这不是“把输入字节全部改成零”的含义。

原 RM 宿主 `60601dab` 在解交错后的 `RADecode` 调用固定传 `0xffffffff`。该调用路径的既有 REA 证据为 `ev_15bd92d0cb09354c3b97881b380fb24516971f44f77cb1b6cfbd440fa6a492c9`，私有原文为 `plugins_followup_20261029/sipr/original-rm-call.c`。因此此文件播放路径不会主动发出无效帧位图；不能据此推断原 DLL 的所有网络调用方或任意数量帧的超大调用都具有相同覆盖。

新私有 API 探针使用合法缓冲区和正常导出，对四种模式各取前 64 个解交错包，分别观察普通重开、重新初始化、Flush、重复设置同 flavor、全零有效位图、交替有效位图及首包长度减一。32 项均正常返回，报告输出长度未超过缓冲容量；每项之后关闭并重开，输出与初始实例逐字节相同。每次 `RADecode` 的位图都从同一常量开始，所以单帧包的 `0xaaaaaaaa` 与全零位图效果相同；它不表示跨调用交替丢帧。

原 DLL 对部分短输入会返回成功并只输出其中完整帧，或成功且零输出。当前 Reader 对损坏容器仍返回错误；本轮不把这种原 API 行为复制为正常文件 EOF，也没有添加无效帧位图或隐藏帧注入。

## 重置边界与旧系统入口

原低码率 `RAInitDecoder`／`RAFlush` 重放与新开实例相同。16k 则存在旧重置差异：本轮 64 包对照重放中有 24 个 PCM 字节不同；两种入口结果一致。状态快照显示 16k 能量历史仍为约 `4.499979/2.499991`，新实例是 `-14/-14`，过去增益也未归零。原重置函数调用 `614a28b0`，后者没有执行构造期 `614a1760` 对这部分历史的初始化。关闭并重开四模式均完全恢复。该观察限定于所测文件及调用序列，不把 24 字节泛化为所有 16k 文件的误差上限。

所有新增探针和原始状态、PCM、日志只存放于 `rebuild/tests/rm_completion_20261105/sipr/`，不加入 Actions 或发布源码测试集合。`stage/run-api.cmd` 是不依赖 Python 的 XP/Win7 入口，含 32 项正常导出调用及三个数值函数对照；该私有入口需要包内原 SIPR DLL 和工作区既有 MSVCR71，不能作为生产依赖交付。`stage/run-reader.cmd` 对六个文件执行 51 组 Reader 回归，完整 16k 与 FATE 截断 16k 分开计数；只需新版 `ttp_rm.dll`，不加载原 SIPR DLL。

探针使用现有 x86、XP 5.01 子系统、VC-LTL 和 YY-Thunks 构建链；API／数值探针的 XP/Win7 导入审计分别通过 157/84 项导入。本机 Win11 已执行 `run-api.cmd` 得到 `SIPR_API_SUITE_PASS cases=32 numeric=3`，并执行首个 `2026.11.05` 候选 DLL 的 `run-reader.cmd` 得到 `SIPR_SUITE_PASS tests=51`。该候选 SHA-256 为 `f66cd7e1974ce3c5c3e3fde26a5f736917f8948fa6adaab16bb126674f667426`。最终构建身份及重新执行的三系统结果见 [统一验收](RM_COMPLETION_20261105.md)。

Reader 回归包括 54 次定位请求、768 次三字节缓冲读取、完整／懒加载、回调开关、定位取消和回滚、截断错误保持及恢复；定位和缓存输出均与当前版本完整输出逐字节比较。未触发底层 I/O 的注入仍标记 SKIP，不计为实际触发的取消。三份截断文件正常读尾、回到零点和失败边界恢复后均保持 `0x8007000d`。XP/Win7 的原 DLL 对照也得到 `SIPR_API_SUITE_PASS cases=32 numeric=3`，日志为 `sipr/xp-api.log`、`sipr/win7-api.log`。最初 VM 复制遗漏原 DLL 的子目录，曾返回加载错误 126；私有测试入口已改为同目录加载并实际通过，不是生产依赖或生产失败。

仍保留少量 1 LSB 差异。此次独立函数逐位一致证明的是列出的正常数值路径，不是整个 SIPR DSP、全部合法码流或丢包隐藏分支逐位一致，也未扩展到独立 RealCodec 导出 ABI 或编码器重建。
